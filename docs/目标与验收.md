# FRD 目标与验收

README 已解除冻结，记录当前目标、建议手段和验收范围；功能状态以实际回归报告为准。目标不得被实现方便性替换，建议手段可根据证据调整。


## 目标

以精简 C# / Avalonia 应用展示真实桌面：捕获 → FFmpeg 编码 → UDP → FFmpeg 解码 → 渲染。保留 localhost 和双机运行。传输比例默认 1×（源桌面原始分辨率），可选 0.75×、0.5×，分别缩放宽高；编码格式要求时向下对齐偶数像素，并显示实际尺寸。主控窗口可自由调整大小，画面等比例显示；窗口大小不改变传输分辨率。适用于静止桌面、网页滚动、局部视频等通用内容，不识别内容语义。1280×720 保留为历史基准测试尺寸。

2026-09-18 扩展：保留 localhost 演示；同一可执行程序通过命令行区分主控与被控，并指定被控监听端口，支持独立机器实测。主控只接收、解码和渲染，被控负责真实捕获与编码；预设、码率和键鼠控制须跨机实际生效。跨机计时必须注明时钟同步估算的不确定度，不能直接相减两台机器的计时器冒充精确单向延迟。

每次更新编译完成后，重启可视 Demo 供用户同步观察；自动回归窗口单独运行并在测试结束后关闭。

仅使用 FFmpeg 编解码后端，废弃 OpenH264 及其他旧编码路径。编码预设由 JSON 定义，编码、解码参数使用可对照 FFmpeg 手册的单行命令行字符串。涵盖 H.264、VP9、AV1，并支持可用的 NVIDIA 编解码。AV2 仍是所需能力；FFmpeg 构建不提供时必须明确标注不可用，不得假回退冒充支持。

主控端手动选择预设，并通过控制通道自动应用到被控端；会话中可切换。主控端通过滑块实时修改码率上限，包含低于 1 Mbps 的档位；须分别显示用户选择、发送端实际生效结果和实际传输速率。无效或不受支持的配置明确报错，保留原有有效会话。

码率控制统一以 Mbps 显示，支持滑动和数值输入，不再固定封顶 5 Mbps。默认可调范围为 0.1–100 Mbps；被控端 JSON 的 `maximumBitrateMbps` 可调整控制范围上限（最高 1000 Mbps），连接时同步给主控。

滑条仅调整编码码率上限，不代表链路速度。编码帧产出后立即通过 UDP 发送，不按滑条数值或其 1.2 倍再次节流；允许瞬时发送速率高于编码码率。开发回归直接验证编码器实际产出码量，不能靠传输限速掩盖编码码率控制未生效；生产运行直接使用已验证的控制逻辑，不增加码率校验反馈环。线上统计包含协议及诊断开销。

控制栏覆盖于画面上方并可折叠；诊断信息独立显示为半透明水印，鼠标穿透、不获取键盘焦点。显示捕获、编码、传输、解码、渲染的最近与平均耗时，计入等待、重组及显式模拟的限速，不将提交绘制冒充绘制完成。主控端可切换独立诊断 UDP 包；视频包结构保持不变，诊断开销单列并计入总发送带宽及显式模拟的限速。视频处理不等待诊断包。

支持手动启停键鼠转发，包含位置、按键、滚轮及释放；Esc 退出控制，断开时释放已按下的键。本机同桌面测试须防止输入回注预览窗口形成循环，并明确它与双机控制的差异。捕获不应造成源鼠标闪烁。

服务端（被控端）每次启动必须通过命令行 `--token` 指定非空口令；缺失、空字符串或纯空白口令直接启动失败，不开始监听。无默认口令，不从 JSON 或上次运行中恢复口令。只有提交相同口令的客户端才能建立远程会话；视频控制、键鼠、鼠标状态及剪贴板通道均需认证，附属通道还必须属于当前主控会话。口令认证不等于通信加密。

被控端每次启动还必须显式指定 `--listen` 和 `--port`，没有监听地址默认值。`localhost` 仅监听 IPv4/IPv6 两种回环；`::` 使用单个 IPv6 双栈 Socket，兼容 IPv4；`::1` 仅为 IPv6 回环。缺失参数或不可恢复异常须向 stderr 输出原因，清理资源并以退出码 1 退出。

主控须及时显示被控端的鼠标形状、热点和显隐状态，包括文本、链接和窗口拉伸指针。鼠标移动不等待视频编码和渲染；缩放后的输入坐标须与源桌面正确对应。

剪贴板同步由用户开启，支持双向文本、文件和目录。文件先完整接收到本机临时目录并校验，再交给 Windows 文件剪贴板；用户在资源管理器粘贴时，由系统处理复制进度、目录合并及同名替换。不得发布未接收完成的文件，也不得把远端路径当作已传输的文件。

带宽估测仅供参考，不自动改变用户预设、码率或分辨率。基于真实媒体包的接收情况、吞吐及延迟趋势提供估计，不用填充流量假装有画面需求；未充分发送时标明只测到下界，空闲时不得宣称精确知道容量。

运动时在用户带宽约束内允许画质下降；静止后优先由成熟编码器自身的帧间预测与码率控制逐渐改善画面。不得自研额外的运动降采样、分辨率轮转、残差增强或固定两秒停发策略。

## 验收边界

- 真实屏幕与完整 UDP 链路不可省略，不跨端共享纹理或原始画面。合成像素只用于独立编解码回归，不替代真实桌面验收。
- 编码上限测试 1、2、3、4、5 Mbps。常规演示和真机运行不施加发送限速；JSON 中原有网络容量、额外包延迟与丢包仅用于明确启用的专项模拟，不增加第二个带宽滑条。
- UDP 包适配 LAN/互联网路径 MTU，避免 IP 分片。尽快处理已到达数据；编码格式确实需要的访问单元重组须如实报告，不得声称任意 UDP 包都能独立解码。
- 帧率上限 30 FPS；不变内容应交给成熟编码器减少重复数据，动态帧率与静止流量需报告真实结果，不能把停止发送等同于已经清晰。
- 稀疏小更新保留平均低于 1 ms 的目标；全区域动态以人眼可接受的清晰度、连续性、及时性及单独实测的多毫秒上限验收。新的后端不得沿用旧路径数字宣称达标。
- 分层统计捕获、转换、编码、排队、限速、网络、解码及实际绘制完成；不能用仅提交绘制、少数快样本或忽略未更新区域证明低延迟。计算耗时与策略等待必须区分。
- 新功能先通过本机短测，再进行双机回归。键鼠测试须验证目标窗口实际收到的输入，覆盖不同窗口大小、传输比例和黑边；剪贴板须验证双向文本、文件内容、目录结构、取消及回环抑制。测试使用专用数据并关闭测试窗口。
- 当前键鼠体验已经用户人工确认，按用户要求暂停自动键鼠测试；继续码率、编解码、双向剪贴板和文件复制等回归，不自动移动鼠标或输入按键。

## 建议手段

- 使用成熟 FFmpeg 编解码器，发送端和接收端分别尽量保留本机 GPU 资源；跨机仍通过 UDP 传输压缩码流。
- 鼠标形状和剪贴板使用独立通道；缓存已知鼠标形状，只发送变化，避免等待视频帧和文件传输。
- 文件接收暂存与用户最终粘贴分开；通过标准 Windows 剪贴板衔接系统复制体验，不另造一套合并、替换界面。

## 必须回答的回归问题

1. 低于或等于 1 Mbps 时，运动停止后是否逐渐清晰？局部更新是否及时？静止流量、重复帧和关键帧各占多少？不得预设必然为零或必然无损。
2. 带宽参考值来自什么测量？是否混入编码、解码、渲染耗时？反馈与探测各耗多少带宽？
3. 运动所需码率超过上限时，编码器是否降质，队列、实际帧率和画面陈旧度如何变化？
4. JSON 预设选择和码率滑块是否真正通过控制通道生效？切换失败能否保留画面？人工可拉伸窗口，测试完成后关闭窗口。
