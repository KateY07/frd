# FRD 目标与验收

README 已解除冻结，记录当前目标、建议手段和验收范围；功能状态以实际回归报告为准。目标不得被实现方便性替换，建议手段可根据证据调整。

当前发布范围（v1.pre9）：保留完整键鼠转发与输入流水发送；增加本机原始分辨率下的低位宽预设、可选 FPS 和启动编解码探测，修复同一会话网络路径暂停导致的过早键鼠通道断开。依赖 .NET 10 x64 运行时，不自包含、不启用 Native AOT。暂不实现自动降码率；下文自动拥塞控制保留为后续目标。


## 目标

### 当前已完成实验的结论（2026-09-20）

本轮“本机完整原始分辨率捕获＋编码延迟极限”探索已结束。固定条件为 Intel Arc 140T、2880×1800、正常彩色、全画面持续变化、约 30 FPS、真实 DDA 桌面捕获；计时从捕获调用开始，到该帧**完整编码包**输出。该口径不包含新画面等待可捕获、UDP、解码、渲染或物理显示扫描。

已测路径中，CPU BGRA→8 条带 LZ4 无损的复测最低：平均 3.40 ms、P95 4.27 ms、19.70 Mbps；60 个计时帧中相邻 59 对均确认内容改变，70/70 帧独立解码后逐字节一致。CPU BGR0→`libx264rgb` 的固定质量复测为平均 8.59 ms、P95 10.02 ms、17.92 Mbps；限制为 2 Mbps CBR 上限时为平均 9.48 ms、P95 11.58 ms、实际约 1.12 Mbps，但画质明显下降。GPU 原始 DDA 纹理→QSV H.264 为平均 10.70 ms、P95 11.13 ms、1.66 Mbps。三条 H.264 路径均完成 70/70 帧解码验证。

结论只适用于上述设备、内容、计时边界和已测实现：当前最低工程下限候选是 CPU LZ4 无损路径，不是端到端或硬件物理下限；当前 FFmpeg QSV 纹理路径没有优于该 CPU 路径。LZ4 的主要成本是 GPU→CPU 映射，约 2.22 ms；QSV 的完整出包调用约 10.57 ms，当前接口不能再拆分驱动等待和硬件编码。没有已知、可验证且预计显著降低该关键路径的新机制前，不继续参数微调或扩展灰度/低位宽实验。完整证据与分层数据见 `tests/CaptureEncodeBench/LATENCY-RESULTS.md` 及其 `results/` 目录。

当前源码接入后的本机可视短测另按完整链路计时，不能与上面的独立编码实验直接比较：2880×1800 的 `h264_rgb_fast` 设 2 Mbps 时，捕获均值 2.21 ms、编码 6.73 ms、捕获到 GPU 完成 20.80 ms，实际发送约 0.60 Mbps，画质受高 QP 限制；`lz4_lan` 的对应数值为 2.04 ms、3.47 ms、18.52 ms，实际发送约 220 Mbps。二者均完成真实桌面、localhost UDP、解码与 GPU 呈现回归；LZ4 适用高带宽 LAN，不适用 1–5 Mbps 限制链路。原始本机报告为 `results/x264rgb-visual.json`、`results/lz4-visual.json`；这些是短时不同画面内容的观测值，不是延迟下限或双机结果。

以精简 C# / Avalonia 应用展示真实桌面：捕获 → 编码 → UDP → 解码 → 渲染。保留 localhost 和双机运行。传输只采用 1× 源桌面原始分辨率；编码格式要求时向下对齐偶数像素，并显示实际尺寸。主控窗口可自由调整大小，画面等比例显示；窗口大小不改变传输分辨率。适用于静止桌面、网页滚动、局部视频等通用内容，不识别内容语义。1280×720 保留为历史基准测试尺寸。

2026-09-18 扩展：保留 localhost 演示；同一可执行程序通过命令行区分主控与被控，并指定被控监听端口，支持独立机器实测。主控只接收、解码和渲染，被控负责真实捕获与编码；预设、码率和键鼠控制须跨机实际生效。跨机计时必须注明时钟同步估算的不确定度，不能直接相减两台机器的计时器冒充精确单向延迟。

每次更新编译完成后，重启可视 Demo 供用户同步观察；自动回归窗口单独运行并在测试结束后关闭。

常规视频预设使用 FFmpeg 编解码，废弃 OpenH264 及其他旧路径；新增高带宽 LAN 候选 `frd_lz4` 是明确标识的 8 条带无损例外。预设由 JSON 定义：FFmpeg 参数为可对照其手册的单行字符串。涵盖 H.264、VP9、AV1，并支持可用的 NVIDIA 编解码。AV2 仍是所需能力；FFmpeg 构建不提供时必须明确标注不可用，不得假回退冒充支持。

启动时在至多 5 秒内探测可用的低延迟有损编解码组合，随后主控端可手动选择预设并通过控制通道应用到被控端；会话中可切换。此启动探测不等于运行时网络拥塞控制，也不保证所有内容下画质和延迟全局最优。LZ4 无损预设不参与自动选择。有损预设通过滑块修改码率上限，包含低于 1 Mbps 的档位；LZ4 无损预设明确显示不限码率并禁用滑块。须分别显示用户选择、发送端实际生效结果和实际传输速率。无效或不受支持的配置明确报错，保留原有有效会话。

码率控制统一以 Mbps 显示，仅保留滑块和数值标签，不再固定封顶 5 Mbps。默认可调范围为 0.1–100 Mbps；被控端 JSON 的 `maximumBitrateMbps` 可调整控制范围上限（最高 1000 Mbps），连接时同步给主控。

有损预设的滑块始终代表用户指定的编码码率上限，自动控制不得移动滑块或改写该上限；内部实际目标码率可在上限内调整，界面分别显示上限、实际生效目标和实际传输速率。检测到拥塞时优先降低新增排队延迟，允许牺牲清晰度；拥塞消退后再逐步恢复码率，不自动切换用户选择的编码预设。此项为 2026-09-19 更新的目标，生产自动控制尚未接入。

编码码率上限不代表链路速度，不按滑块数值或其 1.2 倍虚构一条链路再次节流；允许编码缓冲及瞬时发送突发。真实拥塞反馈所驱动的发送调度与此不同，应联合编码产量避免网络积压。开发回归直接验证编码器实际产出码量，不能靠传输限速掩盖编码码率控制未生效；生产不额外加入编码器正确性校验环。线上统计包含协议及诊断开销。

控制栏覆盖于画面上方并可折叠；诊断信息独立显示为半透明水印，鼠标穿透、不获取键盘焦点。显示捕获、编码、传输、解码、渲染的最近与平均耗时，计入等待、重组及显式模拟的限速，不将提交绘制冒充绘制完成。主控端可切换独立诊断 UDP 包；视频包结构保持不变，诊断开销单列并计入总发送带宽及显式模拟的限速。视频处理不等待诊断包。

支持手动启停键鼠转发，包含位置、按键、滚轮及释放；Esc 退出控制，断开时释放已按下的键。本机同桌面测试须防止输入回注预览窗口形成循环，并明确它与双机控制的差异。捕获不应造成源鼠标闪烁。

服务端（被控端）每次启动必须通过命令行 `--token` 指定非空口令；缺失、空字符串或纯空白口令直接启动失败，不开始监听。无默认口令，不从 JSON 或上次运行中恢复口令。只有提交相同口令的客户端才能建立远程会话；视频控制、键鼠、鼠标状态及剪贴板通道均需认证，附属通道还必须属于当前主控会话。口令认证不等于通信加密。

被控端每次启动还必须显式指定 `--listen` 和 `--port`，没有监听地址默认值。`localhost` 仅监听 IPv4/IPv6 两种回环；`::` 使用单个 IPv6 双栈 Socket，兼容 IPv4；`::1` 仅为 IPv6 回环。缺失参数或不可恢复异常须向 stderr 输出原因，清理资源并以退出码 1 退出。

主控须及时显示被控端的鼠标形状、热点和显隐状态，包括文本、链接和窗口拉伸指针。鼠标移动不等待视频编码和渲染；缩放后的输入坐标须与源桌面正确对应。

剪贴板同步由用户开启，支持双向文本、文件和目录。文件先完整接收到本机临时目录并校验，再交给 Windows 文件剪贴板；用户在资源管理器粘贴时，由系统处理复制进度、目录合并及同名替换。不得发布未接收完成的文件，也不得把远端路径当作已传输的文件。

带宽估测与拥塞反馈用于自动调节内部目标码率，取代旧的“完全手动、估测仅供参考”约定。优先利用真实媒体包及批量接收反馈，允许有明确开销预算的轻量探测；未充分发送时标明只测到下界，空闲时不得宣称精确知道容量。

延迟诊断必须区分：链路低负载基线、相对基线的新增网络排队、程序本地排队及捕获/编解码/渲染耗时。高但稳定的链路固有延迟不是持续降低画质的理由；因发送超过可用容量而新增的排队才是拥塞控制重点。真实网络只能估计基线及排队增量，须标明方向、测量误差与未知状态，不能将 RTT 除以二冒充精确单向延迟，也不能仅凭一个 RTT 值精确归因。目标是尽量控制可避免的新增延迟，不能承诺消除传播延迟或任意公网下固定的总延迟。

运动时在用户带宽约束内允许画质下降；静止后优先由成熟编码器自身的帧间预测与码率控制逐渐改善画面。不得自研额外的运动降采样、分辨率轮转、残差增强或固定两秒停发策略。

## 验收边界

- 真实屏幕与完整 UDP 链路不可省略，不跨端共享纹理或原始画面。合成像素只用于独立编解码回归，不替代真实桌面验收。
- 编码上限测试 1、2、3、4、5 Mbps。常规演示和真机运行不施加人为模拟限速；真实拥塞控制另行验证。JSON 中原有网络容量、额外包延迟与丢包仅用于明确启用的专项模拟，不增加第二个带宽滑块。
- UDP 包适配 LAN/互联网路径 MTU，避免 IP 分片。尽快处理已到达数据；编码格式确实需要的访问单元重组须如实报告，不得声称任意 UDP 包都能独立解码。
- 帧率上限 30 FPS；不变内容应交给成熟编码器减少重复数据，动态帧率与静止流量需报告真实结果，不能把停止发送等同于已经清晰。
- 稀疏小更新保留平均低于 1 ms 的目标；全区域动态以人眼可接受的清晰度、连续性、及时性及单独实测的多毫秒上限验收。新的后端不得沿用旧路径数字宣称达标。
- 分层统计捕获、转换、编码、排队、限速、网络、解码及实际绘制完成；不能用仅提交绘制、少数快样本或忽略未更新区域证明低延迟。计算耗时与策略等待必须区分。
- 拥塞回归分别覆盖高固有延迟但容量充足、低固有延迟但发送超容量、队列已高但不再增长、反向反馈拥塞及容量下降/恢复。联合验证输入时延、视频帧龄/冻结和内部目标码率；不能只保护输入、却饿死视频。用户上限保持不变，码率降低须验证到编码器实际生效及网络队列消退。
- 新功能先通过本机短测，再进行双机回归。键鼠测试须验证目标窗口实际收到的输入，覆盖不同窗口大小和黑边；剪贴板须验证双向文本、文件内容、目录结构、取消及回环抑制。测试使用专用数据并关闭测试窗口。
- 当前键鼠体验已经用户人工确认，按用户要求暂停自动键鼠测试；继续码率、编解码、双向剪贴板和文件复制等回归，不自动移动鼠标或输入按键。

## 建议手段

- 常规视频使用成熟 FFmpeg 编解码器；高带宽 LAN 无损候选使用独立 8 条带 LZ4。发送端和接收端分别尽量保留本机 GPU 资源；跨机仍通过 UDP 传输压缩码流。
- 鼠标形状和剪贴板使用独立通道；缓存已知鼠标形状，只发送变化，避免等待视频帧和文件传输。
- 文件接收暂存与用户最终粘贴分开；通过标准 Windows 剪贴板衔接系统复制体验，不另造一套合并、替换界面。

## 必须回答的回归问题

1. 低于或等于 1 Mbps 时，运动停止后是否逐渐清晰？局部更新是否及时？静止流量、重复帧和关键帧各占多少？不得预设必然为零或必然无损。
2. 带宽参考值来自什么测量？是否混入编码、解码、渲染耗时？反馈与探测各耗多少带宽？
3. 运动所需码率超过上限时，编码器是否降质，队列、实际帧率和画面陈旧度如何变化？
4. JSON 预设选择和码率滑块是否真正通过控制通道生效？切换失败能否保留画面？人工可拉伸窗口，测试完成后关闭窗口。
