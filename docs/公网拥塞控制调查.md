# 公网拥塞控制调查

调查日期：2026-09-19。状态：方案调查；尚未引入新拥塞控制库。本文件区分源码事实、FRD 当前能力和接入建议，不承诺未经实测的公网延迟。

最新安排：用户要求先发布 v1.pre7，暂不实现自动降码率。以下选型与接入步骤保留为后续建议。

## FRD 当前反馈机制与局限

已复核 `FfmpegTransport.cs`：

- UDP 反馈为 72 字节（第 34 行）。完整帧到齐会立即反馈（第 537 行），未完整帧也会调用 `MaybeFlushFeedback`，累计约 20 ms 后反馈（第 546、555–557 行）。
- 接收线程 `Poll(20_000)` 无新包时也调用 `FlushFeedback`（第 462–465 行）；没有待反馈包时直接返回（第 562 行）。因此，“只有完整帧才反馈”不准确。
- 现有反馈是批次聚合，缺少逐包接收状态及到达时间差。它可用于现有交付统计，但不足以直接供给成熟控制器所需的逐包丢失、乱序、时延趋势信息。不能将反馈间隔或 ACK RTT 本身等同于可用带宽。
- 已修复的输入 ACK 流水线解决应用层“前一个事件回复后才发送下一个”的积压；视频拥塞导致的共享链路排队仍需独立解决。

## WebRTC / GoogCC：可借鉴的成熟机制

1. **联合判断拥塞。** 到达间隔减发送间隔的趋势用于判断排队增长；另计算已交付字节速率，并合并丢包估计。不是只根据 RTT 调码率。差分测量不要求两端绝对时钟同步。[延迟趋势](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/goog_cc/trendline_estimator.cc#194)、[吞吐估计](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/goog_cc/robust_throughput_estimator.cc#103)、[综合决策](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/goog_cc/goog_cc_network_control.cc#500)。
2. **有条件探测。** 启动、上限增加、恢复等情况可以探测；拥塞受限时抑制探测。应用流量不足（ALR）期间支持可选周期探测，不能说 WebRTC 空闲绝不探。FRD 若选择静止不发探测，就需等真实流量恢复才能验证增长的容量。[ALR 探测](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/goog_cc/probe_controller.cc#441)、[受限状态处理](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/goog_cc/probe_controller.cc#578)。
3. **控制队列寿命。** WebRTC 支持按优先级配置包 TTL；其另一个默认 2 秒的 `queue_time_limit` 并非硬丢弃期限，还可能提高发送速率清队列。FRD 不应照搬该默认值。源码建议队列过长时在编码前跳帧。[pacer 配置](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/pacing/pacing_controller.h#91)。
4. **降低源头产量。** 网络目标码率更新编码器和帧丢弃器，拥塞窗口压力也可触发编码前跳帧。画质量化交给现成编码器，分辨率/FPS 是另外的适配策略。[编码目标更新](https://webrtc.googlesource.com/src/+/refs/heads/main/video/video_stream_encoder.cc#2420)。
5. **优先级有边界。** 音频可绕过视频 pacing；普通远控输入不自动获得这一特性。DataChannel 使用 SCTP，需要另外处理优先级、拥塞和大消息占用。独立发送队列、线程或 DSCP 均不是公网时延保证。[音频发送](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/pacing/pacing_controller.cc#723)、[RFC 8831 §4](https://www.rfc-editor.org/rfc/rfc8831.html#section-4)。

以上 WebRTC 链接为调查时的官方主线，后续实际复用需另锁定构建提交。逐包反馈可以批量发送，不必每个视频包单发一个 ACK；标准提供序号、接收状态、到达时间和 ECN 信息。[RFC 8888 §3–4](https://www.rfc-editor.org/rfc/rfc8888.html#section-3)。

**接入判断（静态可行性推断，未构建）：**

可将现有 C++ 核心包装为小型 C ABI DLL，由 C# P/Invoke 调用，保留 FFmpeg 编解码后端；没有必要为此整体接入 WebRTC 或 GStreamer。范围包括控制器生命周期、流注册、待发包队列、准许发送时间、已发送通知、接收反馈和目标码率读取。成熟算法主体应直接复用，避免移植改写一套控制器。

这不是无成本替换：需要将 FRD 包映射到控制器期待的 RTP 语义（流标识、包序号、大小、到达时刻及相关标记），并交换其标准化 RTCP 反馈。可评估真实 RTP 封装，或在桥接层提供等价元数据；现有 72 字节聚合反馈不能原样喂入。具体映射、序号回绕、乱序、丢包、队列过期、线程串行化、时钟单位与资源所有权需要测试。

控制器的目标码率还需接入 FFmpeg 现有控制入口；后端是否支持无重启实时改码率须逐一核实。编码参考链必须受保护，不能随意丢弃已编码参考包后继续发送依赖帧。

**未验证：** 本机 C++ 工具链、当前提交 Windows 最小 DLL 构建、C ABI 二进制分发、长期稳定性、目标码率更新与各 FFmpeg 后端联动。本轮只读远端源码，没有保存第三方源代码、构建或引入依赖。

## RDP 与 SRT 的对照

RDP 官方文档说明会持续检测网络带宽和往返时间，据此动态选择编码选项并分配虚拟通道带宽；网络紧张时会调整画质、帧率或压缩方式。它的自适应不是单独改变 FPS。该文档未提供足够细节来复刻完整控制器，也不证明本机 FRD 与 RDP 在同条件下相差多少。[Microsoft：RDP bandwidth / Dynamic bandwidth allocation](https://learn.microsoft.com/en-us/azure/virtual-desktop/rdp-bandwidth#dynamic-bandwidth-allocation)。

SRT 提供直播 pacing、重传恢复、延迟缓冲和过期数据丢弃；实时应用仍须按媒体时间戳产生合理流量。其网络可靠性机制不会自动替任意外部 FFmpeg 编码器调低画质；需要应用联动。对 FRD 的判断是：可参考其明确的过期规则，但不能仅替换为 SRT 就认为交互延迟已解决，缓冲/重传时间也必须纳入预算。[SRT 官方 API](https://github.com/Haivision/srt/blob/master/docs/API/API.md)、[Socket options](https://github.com/Haivision/srt/blob/master/docs/API/API-socket-options.md)。

## FRD 的建议实施边界

- 先保留独立的可靠输入流水线，并让视频排队可观测：记录待发字节、最老数据年龄、交付速率、丢包/乱序和排队趋势。
- 用户最新明确：滑块固定为用户编码码率上限，自动控制不得移动滑块或改写此上限；内部降低实际编码目标并单独反馈界面，恢复后在上限内逐步提高，不自动更换编码预设或传输比例。拥塞时优先控制新增排队延迟，允许降低清晰度。此条取代之前“允许自动调整滑条”的表述；当前尚未接入自动模式。
- 优先编码前控制产量、避免陈旧视频持续排队；发生编码后过期丢弃时，须有参考链恢复规则。输入独立队列不代表视频可以无节制填满底层网络缓存。
- 下一步仅验证 SCReAM 核心加 C ABI 的最小构建、逐包反馈适配和无头网络回归，再决定是否引入。暂不自研完整 GCC，也不承诺公网低于某个固定毫秒数。

具体调节顺序建议：先更新成熟编码器的目标码率，必要时在编码前降低采样频率；只降 FPS 而维持总码率，可能增大单帧体积，不能作为拥塞消退的保证。pacing 用于平滑真实发包，不是把用户滑条再当成一条虚构链路容量。编码器目标、源帧采样、发送队列年龄和实际交付速率需一起验证。

探测优先利用现有业务和批量反馈；允许有预算、有条件的短探测以验证容量恢复，不在已拥塞时继续加探测流量。少量心跳只能测连接/往返时延，无法凭空精确确定空闲链路的全部可用容量。静止期选择不探测时应显示容量未知或旧估计，不把低业务吞吐误认为低容量。

已执行联合瓶颈短测：1 Mbps 共享容量 + 4 Mbps 合成视频负载，FIFO 输入 P95 170.39 ms；代理控制优先后为 31.57 ms，但负载视频 0/105 帧完整。它证明保护输入和降低视频产量都需要处理，不能只看输入延迟或收到的 UDP 字节数。具体模型边界、全双工对照与 5→1→5 Mbps 阶跃结果见 [受限公网回归设计](受限公网回归设计.md#6-已执行生产收发链的共享瓶颈短测)。

## 最新决策：区分固有延迟与拥塞排队

滑块是用户上限 `U`，内部编码目标 `T ≤ U`，真实媒体码率和含协议头的网络发送率另列。拥塞控制下调 `T`，不更改 `U`；恢复时在上限内逐步试探。容量估计须预留协议、反馈和输入等实际开销，不将全部估计网络容量直接用作视频净码率。画质由所选成熟编码器随目标码率调节。

下列量不能混为一个“传输耗时”：

| 观测量 | 含义及边界 |
| --- | --- |
| 低负载 RTT 基线 | 同一路径、扣除可测对端处理等待后的低排队往返估计，包含双向传播及发送等成本；不是精确单向传播时间 |
| 当前 RTT 减基线 | 双向额外延迟的线索，可能包含反向反馈排队或主机调度，不能直接标成视频方向排队 |
| 视频方向相对单向延迟 | 用已发包本地时刻与接收端实际到达时刻关联，扣除该方向历史低排队基线，估计额外排队；固定时钟偏移可抵消，漂移和路由变化仍须处理 |
| 延迟趋势 | 到达间隔减发送间隔的趋势，反映队列变化；队列已经积高后维持不变时，趋势仍可接近零 |
| 本地队列年龄 | 编码前、编码后和发送队列分别直接计时，不能归咎于网络传播；`SendTo` 返回不等于已到达远端 |

保持高而稳定的固有 RTT，且无额外队列增长时，不应仅凭 RTT 高反复降画质。在途字节多也可能只是长距离链路正常的带宽时延积；不能全部算为排队。相反，队列已处高位时，不能因为增长趋势回零就判断恢复。相对基线测量与联合拥塞反馈符合 [SCReAM 的排队时延测量说明](https://www.rfc-editor.org/rfc/rfc8298.html#section-3.1)；[实时媒体拥塞要求](https://www.rfc-editor.org/rfc/rfc8836.html#section-2) 也要求降低自身引起的延迟，并适应路由及容量变化。

当前实现的限制：`DelayTrendMs` 只是相邻反馈端点差分的 EWMA，不是已有排队毫秒数；`ClockEstimate` 的四时间戳用于 TCP 控制通道时钟估算，不等于 UDP 视频路径的精确单向基线。现有 UDP 反馈携带接收时刻，反向反馈排队通常使信息变旧，不会直接增加同一对视频包的前向到达间隔。诊断应另外显示反馈年龄；不能将旧反馈冒充当前队列状态。

当前发送戳在 `SendTo` 之前、接收戳在 `ReceiveFrom` 返回之后，包含部分主机调度和内核等待，必须标成“应用可见额外延迟估计”，不能冒充路由器队列的直接测量。若增加 UDP RTT 观测，需携带接收至反馈发出的等待时长，避免把批量反馈等待算成线路传播。具体时间戳位置及正反向不对称的测量边界参见 [RFC 7679](https://www.rfc-editor.org/rfc/rfc7679.html#section-3.7.2)。

真实网络的“额外排队”只能估计，不具有模拟器中的全路径真值。启动时已经拥塞、链路改道、无线调度及其他流量都可能影响基线；基线需持续校正并标记未知/过期，不能把一次增大立即学习成新的固有延迟以掩盖拥塞。只有延迟升高而证据不足时，应明确显示归因不确定，控制器可保守退让，但不能声称精确证明由本程序超发导致。
