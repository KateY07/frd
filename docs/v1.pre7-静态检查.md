# v1.pre7 静态检查与回归记录

检查范围：生产 `RemoteInputClient` 的流水发送、回执和关闭处理，以及 `FfmpegUi.SendInputLoopAsync` 的顺序发送与异步结果观察。以下为已存在报告的核对结果，不把历史双机回归计作本次验证。

## 静态检查

| 项目 | 结论 |
| --- | --- |
| 顺序与界限 | 写入锁保持协议请求顺序；最多 64 个请求在途，业务 ACK 独立按编号匹配；单请求 ACK 超时为 5 秒。 |
| pending 与槽位 | 登记、完成和全体失败的移除受同一锁保护；写入前退出归还本地槽位，已登记请求由回执或全体失败路径归还。未发现重复释放或确定的死锁。 |
| 故障与关闭 | 断线、错误回执、写入后取消及超时关闭连接并结束所有待确认任务；被控端连接清理执行 ReleaseAll，失败保留日志。 |
| 关闭前取消缺陷 | 已修复：关闭请求尚未取得槽位/尚未写入时取消，原先只会清除本地 Enabled。现在同样关闭 TCP，避免远端持键遗留。 |
| 远端拒绝关闭 | 已修复：保留拒绝结果，同时关闭连接，令被控端清理路径再次尝试释放。 |
| 延迟 enable 回执 | 版本号检查防止较早的启用回执覆盖较新的关闭状态。 |
| UI 工作线程 | 顺序等待请求写入，分别观察 ACK；首个异常关闭客户端并取消等待，空闲工作线程能够退出；结束前等待剩余观察任务。未发现确定的自等待或漏观察故障。 |

静态结论针对所列路径，不等同于所有并发时序的形式证明。`QueueAsync` 外层完成仅表示写入阶段完成，返回的内层任务才是远端业务结果；业务 ACK 不表示目标程序已重绘。

## 性能与模型边界

输入延迟代理分别读取完整请求/回复，以绝对到期时间调度，不通过每包串行睡眠人为限制吞吐。Windows 实际唤醒可能晚于配置值，报告保存实际调度延迟。

持续 120 Hz 输入、仅回复方向附加延迟的可比场景：实际回复等待约 30.8 ms 时，串行平均生成→模拟注入约 2727.28 ms；流水为 0.27 ms、P95 0.37 ms。请求与回复各配置 25 ms 时，实测生成→模拟注入平均约 31.54 ms，生成队列 P95 约 0.18 ms。前者证明消除了串行 ACK 积压，后者仍保留实际传播等待；两者都不是远程屏幕响应时间。

7 个受限网络场景使用生产输入协议和 UDP 分片重组，视频是合成字节负载，没有编解码或 GPU 呈现。TCP 头部与反向传输 ACK 是明确计费假设，不是抓取的内核 TCP 包，也没有模拟真实 TCP 丢包重传。内部优先队列只代表实验调度，不能当作公网 QoS 保证。

尤其是 `shared-airtime-video-control-first`：输入平均约 27.24 ms，但计时负载期间完整视频帧为 0。该场景完整性通过，仅说明输入及启动前 UDP 冒烟检查有效；视频结果必须记为饥饿，不能写成“低带宽体验通过”。后续计划见 [受限公网回归设计](受限公网回归设计.md)。

## 交付限制与发布核验

- 没有接入自动降码率、自动预设切换或新的生产拥塞控制；实验调度器不进入正式视频传输路径。
- 没有新的正式 UI。本机 Demo 保留专用滚轮/键盘目标；真实网页输入与虚拟指针仍属于独立测试及设计工作。
- 本机模式按连接 peer 地址识别。经 localhost 端口隧道连接异机时，也会按本机模式限制输入；普通异机 IP 直连不受此限制。
- 本轮未新增 LAN、RDP 对比、真实应用操作到画面 GPU 完成测量，未重跑完整双机剪贴板和硬件编码矩阵。
- 发布前重新生成单文件 Demo；主项目和 Demo Release 构建均为 0 警告、0 错误。
- 发布前重新执行流水可靠性短测，32 项全部通过，报告计时 5.38 秒；证据为 `results/release-v1.pre7/input-pipeline.json`。没有重复完整网络矩阵。
- 最终便携包的 CLI 版本、帮助、参数错误退出及 ZIP 完整性由发布流程检查，结果保存在本机 `results/release-v1.pre7/`；包 SHA-256 位于 `artifacts/v1.pre7/SHA256SUMS.txt`。源码记录不预填尚未生成的包散列或提交号。
