# 受限公网输入与视频回归设计

状态：完整矩阵为设计；已实现并执行下文的五组应用层联合短测，尚未执行 IP 层完整矩阵。先验证拥塞根因，再比较成熟策略；当前未启用生产自动码率。最新约定为滑块固定用户上限，自动调节内部实际码率；拥塞时优先延迟而非清晰度，仍须完成成熟控制器与编码器响应验证。

## 1. 同一瓶颈，两种网络模型

拓扑：`主控 C ⇄ 双向瓶颈代理 ⇄ 被控 H`。接入生产 `RemoteInputClient/Server`、`UdpVideoSender/Receiver`，视频使用真实 FFmpeg 码流；禁止另开不受限的控制捷径。

| 方向 | 必须进入该方向瓶颈的流量 |
| --- | --- |
| C → H | 输入、视频接收反馈、编码配置命令及相关 TCP ACK |
| H → C | 视频 UDP、输入业务 ACK、配置回复、诊断包及相关 TCP ACK |

- **全双工**：两个独立容量与发送队列。默认两方向各为 C；视频与输入方向相反，但输入业务 ACK 与视频同向。不能把下行拥塞直接算成上行输入排队。
- **共享空口简化模型**：两个方向共用一个容量 C 和串行发送资源；排队与字节成本统一核算。只代表双向竞争，不模拟 Wi-Fi 争用、重传、速率选择等完整无线行为。

正式拥塞试验使用**不终止 TCP 的 IP 层转发/成熟网络仿真后端**，让真实 TCP 数据、ACK、重传均经过瓶颈；具体后端沿用技术调查的选型结果。已有 JSON 帧延迟代理只保留为输入排队单项基线：它看不到两段本机 TCP 的真实 ACK，不能冒充公网 TCP 丢包/重传试验。禁止通过删除或乱序 TCP 应用帧“模拟丢包”；TCP 损伤应作用于 IP 包，由真实协议栈恢复有序字节流。

## 2. 参数与代理正确性

容量使用十进制 Mbps，按实际 IP 包长度计费，包含协议头、反馈、ACK、重传；无线模型明确不计 MAC/PHY 开销。以抓包/计数确认两方向均未绕过代理。

容量、传播延迟、抖动、独立随机丢包、乱序分别配置，保存随机种子。包先竞争发送容量，完成串行发送后再经历传播延迟；用绝对到期时间调度，不能为每个包重复串行睡一个 RTT。基线队列为 FIFO：固定字节上限相当于初始容量下 300 ms，变速时不扩容；溢出丢包与随机丢包分开统计。先记录实际调度误差，不用配置值替代实测。

代理先自检：容量积分与实际转发字节相符，容差不超过一个最大包；无损时无重复、无丢失；TCP 到达业务层保持原序；UDP 乱序/丢包与注入记录对应。单包串行时间 `包字节数 × 8 / 容量` 属于真实成本，不能从测量中删去。

## 3. 最小矩阵

固定相同编码预设、1280×720、30 FPS 上限和持续运动素材；使用真实编码器，不识别网页内容。记录实际产生码率，不能将“上限 5 Mbps”当成已经满载。素材无法压满时该场景标记未覆盖，或显式加入单独统计的竞争流。

每个固定场景 10 秒：前 2 秒仅输入 60 Hz；随后 4 秒满载视频＋60 Hz 输入；最后 4 秒满载视频＋120 Hz 输入。使用有编号的按键按下/释放和滚轮，接收端为无头记录器，不操作人的系统鼠标。初始视频编码上限保持 5 Mbps，用于暴露超载行为。

| 组 | 网络条件 | 数量 |
| --- | --- | ---: |
| 空载参考 | 两方向传播各 25 ms，无限容量、无损伤；同样跑完整负载阶段 | 1 |
| 固定瓶颈 | 0.5 / 1 / 2 / 5 Mbps；全双工与共享模型各跑；传播各 25 ms | 8 |
| 损伤 | 1 Mbps；各方向传播 50 ms，额外随机延迟 0–10 ms，独立丢包 1%，另对 1% 的包额外延后 20 ms；两模型各跑 12 秒 | 2 |
| 容量突变 | 5 → 1 → 5 Mbps，每段 8 秒；传播各 25 ms、无随机损伤；全程满载视频＋120 Hz 输入 | 2 |

先跑 1 Mbps 两模型约 20 秒短测；通过代理自检后完整矩阵约 3 分钟，不做所有参数的笛卡尔组合。损伤组另记实际乱序比例，配置的延后比例不等于实际乱序率。短测仅筛查明显缺陷，候选策略通过后对关键场景换种子重复。

## 4. 一份报告，分清测量层次

| 项目 | 必须记录 |
| --- | --- |
| 输入 | 生成→生产发送队列出队→写入→接收注入→业务 ACK；每段平均/P95/P99/最大、最老事件年龄、在途数、编号及按下/释放顺序 |
| 视频 | 编码完成→发送队列等待→首/末包→重组→解码；按帧报告年龄、排队字节/时间、丢弃与恢复原因；不能只统计幸存帧 |
| 网络 | 每方向 200 ms 和 1 s 的发送率、接收率、有效负载 goodput、协议/重传开销、丢包及乱序；反馈生成到被控端采用的年龄与中断时长 |
| 编码调整 | 命令发出、接收、编码器应用、首个使用新配置的帧、实际输出码率收敛时间；按预设/VBV及观测窗口解释瞬时突发 |

同机使用单调时钟；双机只直接相减同一时钟上的时间，跨机单向值必须附同步方法与误差。业务 ACK 不是目标应用处理或显示完成；虚拟指针本地更新也不是远端响应。

报告分别标明：**模型队列成本**、**真实 socket/生产收发链**、**真实屏幕变化到匹配画面 GPU 完成**。前两项先无头执行；最后一项只挑已通过的关键场景，用真实应用变化及画面标记关联后再测，不把网络模型结果冒称最终渲染延迟或物理屏幕扫描时间。

## 5. 断言与比较方法

1. **可靠性是硬断言**：连接未中断时，全部输入恰好到达一次且顺序正确，最终无按键残留；断线必须明确失败并释放状态，不能悄悄漏事件。保留未完成/超时样本与最长冻结时段。
2. **排队不得被平均数掩盖**：无随机损伤的候选策略，主控生成队列 P95 < 30 ms；扣除实测传播/串行成本后的输入时间，末四分之一均值不得较首四分之一增加 30 ms 以上。另报视频帧龄、反馈年龄及最长无新帧时间，不据此自动宣称画面合格。
3. **允许基线失败**：固定 5 Mbps 视频遇到更低容量，预期出现排队、溢出和较老画面；共享模型还可能拖慢输入。串行等待 ACK 的旧输入路径预期积压；流水发送应消除该项积压，但不能消除真实链路排队或 TCP 重传等待。损伤组不套用无损场景的 30 ms 结论。
4. **逐项验证策略**：先测“无新增优化”；随后只在测试配置中逐个比较成熟反馈控码率、发送节奏、有界视频队列/过期数据处理和输入调度。相同素材、种子、容量时间线，比较上述延迟与 goodput，并确认未靠丢输入、饿死视频或绕开瓶颈获胜。容量恢复后单独测恢复时间及振荡。
5. **公平说明优先级**：默认瓶颈不识别应用优先级；另开的优先调度实验只代表受控设备支持该策略。程序内部队列优先或 DSCP 标记，不等于公网路由器保证优先。正式自动控制须在成熟方案调查和这套对比后再决定。

设计参考已核对的 [RFC 8868 §3–4](https://www.rfc-editor.org/info/rfc8868/) 中发送/接收/goodput、排队、丢弃及收敛指标，以及 [RFC 8867 §5.1、§5.3](https://www.rfc-editor.org/info/rfc8867/) 的容量变化与反馈方向拥塞场景；本文是 FRD 的缩短回归矩阵，不宣称完成 RFC 的全部评估。[RFC 8836 §2](https://www.rfc-editor.org/info/rfc8836/) 也明确指出路径可能不采纳 DSCP，并应关注反馈通道异常。

## 6. 已执行：生产收发链的共享瓶颈短测

工程 `tests/ConstrainedNetwork/`，报告 `results/input-latency/constrained-network.json`。报告计时 21.49 秒，五组完成输入完整性、有序性及独立 UDP 分片重组校验。**报告 Passed 只表示这些检查通过，不表示拥塞视频已可用或自动控制已达标。**

使用修复后的生产 TCP 输入流水线和 UDP 收发器，合成 4 Mbps / 30 FPS 的帧负载（不编解码）；持续生成 60 Hz 输入。固定传播每方向 20 ms，按实际消息/数据报长度核算有限容量；UDP 排队上限 150 ms，溢出/过期只丢视频。控制回复和接收反馈也进入同一模型。先完成会话握手和独立 4 KB 多包 UDP 校验，再计负载统计。

| 条件 | 生成→mock 注入 P95 | 生成→业务 ACK P95 | 完整负载帧 |
| --- | ---: | ---: | ---: |
| 1 Mbps 共享容量，无视频 | 22.96 ms | 45.26 ms | 不适用 |
| 1 Mbps 共享容量，4 Mbps 视频，FIFO | 170.39 ms | 336.08 ms | 1 / 105 |
| 相同负载，代理优先控制流 | 31.57 ms | 58.88 ms | **0 / 105** |
| 上下行各 1 Mbps，全双工 FIFO | 22.74 ms | 194.73 ms | 1 / 105 |
| 共享容量 5→1→5 Mbps，控制优先 | 30.84 ms | 57.97 ms | 52 / 150 |

共享 FIFO、共享优先、全双工的输入模型队列等待 P95 分别为 148.62、9.45、0.26 ms，差异主要来自排队。反向输入可正常到达时，顺向 ACK 仍可能被视频阻塞；这是保留流水发送的意义，不能再因 ACK 慢就逐事件停发。

三种视频负载的 UDP wire goodput 约为 0.662、0.678、0.812 Mbps，但完整帧有效负载仅约 0.034、0、0.034 Mbps。**收到很多 UDP 字节不等于得到可解码视频。** 控制优先场景显式标记 `VideoStarved=true`，没有完整帧时帧龄为 null，不能用幸存帧的低延迟掩盖冻结。优先级只保护部分控制交互，仍必须降低视频产量并限制陈旧数据。

局限：代理终止并重建本机 TCP，按 MSS/协议头/反向 ACK 显式核算开销，未测真实内核分段、重传、拥塞窗口。优先模式代表受控设备能够识别流量，并非公网保证；固定传播之外包含操作系统调度误差。没有真实 FFmpeg 码流、随机损伤、图像回显或 RDP 对测，不能替代上面的完整矩阵。初测报告 `constrained-network-initial.json` 与启动校验失败证据保留；最终运行没有内部错误。

## 7. 码率滑条响应需独立计时

现有 UI 有 150 ms 防抖，命令还要等发送端编码循环处理；libx264 通常原上下文更新，其他当前未支持动态修改的后端会重建编码器。接收端 ApplyAsync 还可能创建备用解码器。这些是静态分析，尚没有本轮逐预设的切换时间测量。

后续分别记录拖动/命令时刻、目标端收到、编码器应用、首个新配置帧、实际码率收敛；不能把滑块位置改变或一次控制 ACK 当成整个网络已经降载。编码 VBV 允许短时突发，已进入网络的旧数据也不会因降码率被撤回。自动控制直接更新内部编码目标并遵守用户上限，不通过模拟拖动界面滑块实现；记录检测拥塞→内部目标变化→编码器生效→队列消退的完整响应时间。

## 8. 固有延迟与新增排队的专项对照

最新目标是优先抑制可避免的新增排队，滑块始终保留用户上限。以下断言约束后续控制器，不能将网络模型通过等同于控制器已经通过。

| 条件 | 应验证的行为 |
| --- | --- |
| 高传播延迟、容量充足 | 测得基线较高但额外排队较低；不只因绝对 RTT 高就持续降低码率 |
| 低传播延迟、视频超出容量 | 新增排队可见，控制器降低实际编码目标；随后验证队列及视频帧龄消退，而不只看配置 ACK |
| 排队增长后维持高位 | 延迟趋势归零不能判成恢复，额外排队仍应可见；不得立即升回原码率 |
| 只有反向反馈排队 | 前向到达时间与反馈年龄分开；不把额外 RTT 全部归因到视频方向 |
| 路由基线变化或测量失效 | 标记基线重新估计或未知；不在满载拥塞时直接抬高基线掩盖队列 |

模型中传播延迟和按包长/容量计算的发送时间是已知设定，入队/出队及最终交付时刻为本机实测；报告需分别列出。真实公网没有这些全路径真值，发送/接收应用时间戳还混入主机内核与调度，必须将额外延迟标为估计。无头模型测试没有真实编码器，无法验证自动调码率响应与最终视觉效果；后续必须使用真实 FFmpeg 码流连接控制器再回归。
