# 鼠标移动与视频背景码率定向测试

运行 `dotnet run --project tests/ConstrainedNetwork/ConstrainedNetworkTests.csproj -c Release -- results/input-latency/mouse-follow-sweep.json --mouse-sweep`。

测试复用生产 TCP 输入客户端/服务端和 UDP 视频分片/重组，在一条模拟的 5 Mbps 双向共享链路上，以 120 次/秒发送鼠标移动，同时分别施加 0、1、3、5、7 Mbps 的 30 FPS 合成视频负载；最后再测一次 7 Mbps 下控制包优先。记录移动产生到接收端模拟注入、输入确认、视频整帧到达、丢包及链路排队。模拟链路每方向传播 10 ms，视频队列超过 150 ms 时丢弃视频包。

这不是物理鼠标或屏幕跟随测试：模拟注入不移动系统光标，也没有编码、解码、渲染、真实 Wi-Fi、TCP 丢包重传或预览 UI 的待发送移动合并。结果只能隔离网络排队与输入协议的关系，不能直接认定当前双机体验的实际原因。结果文件保留每种条件及其完整性检查。

2026-09-20 的一次完整运行见 `results/input-latency/mouse-follow-sweep-20260920.json`，六个条件及完整性检查均通过：

| 视频提供码率 | 移动→模拟注入 P95 | 确认 P95 | 完整视频帧 |
| --- | ---: | ---: | ---: |
| 0 Mbps | 11.32 ms | 22.15 ms | 0/0 |
| 1 Mbps | 13.40 ms | 28.77 ms | 90/90 |
| 3 Mbps | 49.75 ms | 91.64 ms | 90/90 |
| 5 Mbps | 157.42 ms | 304.76 ms | 9/90 |
| 7 Mbps | 157.40 ms | 305.27 ms | 4/90 |
| 7 Mbps、控制包优先 | 13.23 ms | 25.66 ms | 2/90 |

该模型在视频排队超过 150 ms 时主动丢视频包，所以 5/7 Mbps 条件的输入延迟没有继续无限增长。控制优先虽改善输入，但视频仍严重失效；完整体验必须同时控制视频供给和旧帧积压。
