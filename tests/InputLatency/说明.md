# 输入协议延迟基准

使用真实 `RemoteInputClient`、`RemoteInputServer`，由 `IRemoteInputInjector` 的测试实现记录注入时刻。**不调用 Windows SendInput，不移动鼠标，不发送真实按键，不创建窗口。** 不包含视频捕获、编解码、渲染，不连接远程机器。

```powershell
dotnet build tests/InputLatency/InputLatency.csproj -c Release
dotnet tests/InputLatency/bin/Release/net10.0-windows10.0.26100.0/InputLatency.dll results/input-latency/input-ack-serial.json
dotnet tests/InputLatency/bin/Release/net10.0-windows10.0.26100.0/InputLatency.dll results/input-latency/input-ack-pipeline.json --pipeline
```

当前版本使用完整帧绝对到期时间调度，读取与延后写出分离，避免每条 ACK 串行睡眠造出额外吞吐瓶颈。基础 16 场景的额外回复延迟为 0、5、10、25 ms；`--pipeline` 另测两个双向各 10/25 ms 的 120 Hz 场景。`Task.Delay` 并不保证此精度，报告包含实际转发延迟，不能把配置值当实测 RTT。该代理不模拟真实 TCP 丢包重传，也没有共享视频带宽限制。

每个延迟档包含 16 个独立事件、持续两秒的 120 Hz 滚轮、60 Hz 键事件和 64 个突发事件。serial 模式复现旧的逐 ACK 消费；其中突发加基准器串行闸门，因为生产客户端已支持多条在途。pipeline 模式按序等待 `QueueAsync` 外层写完，独立观察内层真实 ACK，所有 ACK 完成后才结算。两种模式均验证编号完整且保序。测试没有执行实际 UI 队列、坐标映射、512 上限或移动合并，不能推广为完整桌面操作测试。

时间均来自同一进程的 `Stopwatch`。生成时刻是实际创建事件时刻，报告另列计划节奏的迟到量和实际生成频率。`GenerationToInjection` 为生成到 mock.Inject；`GenerationToAck` 为生成到 ACK 完成；`SendToAck` 为调用 SendAsync 到完成。**突发用例的 SendToAck 包含客户端 gate 排队，不能当作网络 RTT。** 串行用例的 `MaximumGeneratorQueue` 是基准 FIFO 最高长度；`MaximumPendingInjection` 包括已经交给客户端、尚未注入的事件。

## 2026-09-19 修复对照

相同新版 relay、120 Hz 滚轮、请求回复延迟 25 ms（实测 ACK 周期约 31.2 ms）：serial 生成→mock 注入平均 2727.28 ms / P95 5186.56 ms；pipeline 平均 0.27 ms / P95 0.37 ms。此场景正向没有人为传播延迟，因此小于 1 ms 只说明消除了等 ACK 的积压，不代表公网端到端延迟。

双向各请求 25 ms 时，实际生成→注入平均 31.54 ms / P95 34.57 ms、ACK 平均 62.89 ms，发送前 FIFO 排队 P95 0.18 ms。18 个 pipeline 场景全部通过，耗时 23.3 秒；serial 16 个场景复核耗时 33.3 秒。结果分别为 `input-ack-pipeline.json` 和 `input-ack-serial.json`；原始 baseline 不覆盖。

## 2026-09-19 首次测量

完整报告 `results/input-latency/input-ack-baseline.json`，16 个用例耗时 33.6 秒，未运行视频编码负载。

| 条件 | 实际 SendAsync 平均耗时 | 生成到注入平均 / P95 / 最大 | 最大 FIFO |
|---|---:|---:|---:|
| 0 延迟，120 Hz 滚轮 | 0.68 ms | 1.00 / 1.92 / 4.02 ms | 3 |
| 0 延迟，60 Hz 键事件 | 0.65 ms | 0.49 / 0.75 / 1.47 ms | 2 |
| 请求额外 5 ms，120 Hz 滚轮 | **15.65 ms** | 867.79 / 1659.85 / 1741.23 ms | 112 |
| 请求额外 25 ms，120 Hz 滚轮 | **31.32 ms** | 2734.94 / 5214.97 / 5486.00 ms | 176 |
| 请求额外 25 ms，60 Hz 键事件 | **31.22 ms** | 861.08 / 1642.22 / 1718.70 ms | 56 |

Windows 计时调度使请求 5 和 10 ms 的 relay 延迟实际都接近 15 ms，请求 25 ms 实际接近 30.5 ms。实际生成频率为 119.4–120.3 Hz、59.6–60.0 Hz；生成节奏的最大迟到约 16 ms，在零延迟对照中未形成持续积压。

结论：无额外网络延迟时，真实协议到模拟注入器的耗时很小；但生产客户端持有 gate 直到 ACK，UI 也逐事件等待 ACK，允许的持续输入吞吐受 RTT 限制。实测 ACK 约 15.6 ms 时只能处理约 64 个事件/秒，120 Hz 的不合并输入因此迅速积压。这里确认的是机制及触发条件，**尚未证明用户当前网络存在这种 RTT，也未测 RDP、真实 Windows 注入或画面反馈延迟。**
