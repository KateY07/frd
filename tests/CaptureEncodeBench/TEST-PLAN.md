# 原始桌面捕获＋编码验证程序

本程序独立于 FRD 生产代码。信息收集程序已取消。每项实验先说明技术策略和参数，再编译运行、分析结果，不临场无依据地改方案。

## 当前目标：工程延迟下限，而非仅仅跑通

**用户目标原文：在本机 Intel Arc 140T、2880×1800 原始分辨率正常彩色、30 FPS 条件下，测得CPU/GPU方案的屏幕捕获+编码的延迟下限。**

以下是为目标服务的实验方案，不是追加的目标约束。5 Mbps、H.264、线程数量和候选路径数量均不是目标限定；现有参数只是已实施的基线。调整实验方案时先写明理由和策略。无需把所有候选路径逐一修好，更不以生产级后端修复、发布或改造 FRD 为前提。

依照此前明确的口径，主指标为捕获至完整编码输出的平均延迟。有效低延迟策略已经落实，且有证据支持没有显著继续提升空间时，可以认定条件限定的工程下限；不要求证明芯片绝对物理极限。当前历史数值仍为阶段性观测。

`completed` 仅表示一次采样和码流正确性检查完成。它与最终下限认定分开；报告必须另列 `LatencyFloorAssessment`，不能从单次跑通自动升级。NVENC 本机不具备运行条件，只记录能力限制，不反复尝试，也不冒充测得下限。

## 开始测量之前固定的策略

| 路径 | 减少延迟的固定策略 | 必需成本与待核实项 |
|---|---|---|
| CPU RGB | DDA 后一次 staging 回读，映射内存直接借用给 x264rgb；不逐行复制、不应用层转 YUV；ultrafast、zerolatency、无 B 帧/前瞻 | 本机桌面不在系统内存，回读不可称为零拷贝；核实 SIMD 生效和切片线程，没有帧级排队 |
| CPU YUV | 同样借用映射输入，复用转换缓冲，四线程 BGRA→YUV420P；x264 同上 | 回读和格式转换分别计时；不得把转换藏进“捕获” |
| GPU NV12→CPU | 同一 D3D11 设备 VideoProcessor 转 NV12，减少回读数据，再借用映射 NV12 给 x264 | GPU 提交与 Map 等待分开；GPU 转换＋回读是否胜过 CPU 转换要用一致输入比较 |
| CPU NV12→QSV | staging 回读、复用 CPU NV12 转换缓冲；QSV veryfast、low_power=1、async_depth=1、零前瞻、零 B 帧 | 明确包含上传，仅作系统内存硬编码对照，不能冒充纹理直通 |
| GPU NV12→QSV | 同设备 GPU 转 NV12，直接映射 QSV surface，无原始像素 CPU 回读；QSV 参数同上 | 修复 session 生命周期和损坏码流；分别定位 GPU 未完成工作与编码同步 |
| GPU RGB→QSV | 借用原始 BGRA 纹理并保持生命周期，直接映射 QSV，无应用层颜色转换；QSV 参数同上 | 核实驱动内转换/同步开销；接受 RGB 输入不等于内部没有转换 |

共同策略：不累计待编码帧，一帧完成后再提交下一帧；保持当前帧纹理/映射内存存活至编码器释放引用；不通过不等待真实完成来缩短计时；默认不添加 GPU fence。逐帧日志不写磁盘，解码、图像对比和报告输出放在采样之后。初始化、首帧、稳态分别记录。

现有四线程是基线，不预先认定最佳。CPU 线程 1/4/8 是预先列明的候选对照，不是必须全部完成的目标。只有能回答具体瓶颈问题时才执行相应对照，保持其他条件一致。AVX2 属于成熟编码器的指令优化，不是另一种编码器。

## 执行顺序与停止条件

1. **静态落实检查**：逐条核对复制、转换、帧队列、缓冲所有权及实际编码选项。补齐 send_frame、receive_packet、码流复制与额外队列检查的独立计时；这些计时是 API 边界，不直接等同 GPU 纯执行时间。
2. **正确性处理**：损坏码流不能作为有效成绩。保存证据，只修复妨碍有意义测量的问题，不要求把所有失败候选修好。QSV loader 隔离绕过若只影响计时外初始化，可以在明确限制并验证计时路径不受影响后用于本次探索；不把生产生命周期修复扩展为独立目标。更换码率或 VBV 必须先声明新的实验条件，不能冒充原条件下修好了损坏问题。
3. **一致输入**：准备一份固定的真实桌面操作序列，覆盖小区域变化、滚动、局部视频；按相同顺序在原始尺寸桌面回放，再经 DDA 真实捕获。记录序列及帧标识、丢过的更新，不把直接读取离线视频当真实捕获。用于对照的输入无法对应时不作性能排名。各场景分别报告，不用不同场景混合平均掩盖差异。
4. **预定诊断**：对 QSV 编码 API 内仍未解释的耗时，只做一次针对性跟踪，区分前处理未完成、提交、等待硬件、轮询/调度。默认路径与显式 GPU fence 诊断各跑一次，后者只定位等待归属，不作为新的“更快方案”。只有证据指向 FFmpeg 包装额外成本时才加入固定参数的官方 oneVPL 对照，并在运行前补充具体方案。没有依据不扩大后端矩阵。
5. **短测复现**：每条已修复路径、每个固定场景预热 10 帧、采样 60 帧，做两次独立短测。两轮均值差超过较小均值的 10% 或 0.5 ms（取较大者）时只补一次；仍不稳定，标记未能认定并解释原因，不无限重测。该门槛是工程复现规则，不是统计置信区间。报告各轮及合并平均、P50/P95/最大、码率、质量、GC；不挑最低一次或最低单帧冒充平均下限。
6. **下限认定**：码流正确、计时完整、策略生效、复现稳定、主要耗时有证据解释，并排除了有依据的显著改善路径，才认定“限定条件下相当确定的工程下限”。1 ms 或总耗时 10% 只作为安排实验优先级的参考，不是用户新增的验收数值。目标没有规定必须低于 7 ms。无法排除明显改善方案时，不宣称没有空间。

遇到新的方案变更，先写“问题证据、预计收益、固定变量、一次性验证办法”再改代码/运行。测试中的正常动作只修 BUG；不临时换内容、算法、画质或参数。码流正确性通过只是上述第 2 步的一个条件。

## 2026-09-19：固定质量对照，一次性方案

现有 GPU RGB→QSV 的一次分段结果：60 帧平均捕获至出包 17.578 ms，其中 `avcodec_send_frame` 17.203 ms，取包 0.004 ms，复制 0.050 ms。提交耗时约 11 ms 和 21 ms 两组；从第 37 帧起输出包反复为约 20,830 字节但提交耗时保持约 21 ms，不能仅从码流字节数推断原因。

静态核查：FFmpeg 8.1.2 QSV `veryfast` 对应最高速度 TargetUsage；`async_depth=1` 的 `ff_qsv_encode` 在当前帧提交后调用 `MFXVideoCORE_SyncOperation` 等待，因而提交阶段包括驱动等待。当前相等的 `bit_rate` 和 `rc_max_rate` 使 FFmpeg 选择 **CBR**，即此前的“5 Mbps”基线实际上带有恒定码率控制。x264 的 `ultrafast`、`zerolatency` 与 AVX2 已生效，CPU 路径需要 staging 回读。

有依据的候选收益：移除 CBR 可能减少码率控制/填充工作；无需更换编码器或屏幕尺寸。下一次只新增明确的固定质量模式，并选 `cpu-rgb`、`cpu-yuv`、`gpu-rgb-qsv` 三条原路径。GPU QSV 使用 CQP 26；CPU x264 使用 CRF 23。这是各编码器适用的固定质量预设，**不宣称两者具有相同画质，也不据此做 CPU/GPU 性能排名**。保留 30 FPS、2880×1800、x264 ultrafast/zerolatency/4 线程、QSV veryfast/low_power/async_depth=1、零 B 帧、原始彩色及既有计时与严格解码。记录实际码率和参考帧误差；质量明显不可接受时不得称达到有意义的下限。新模式不作为用户目标中的码率上限。

只编译一次、三条路径各采样一次，先看正确性和耗时级别。若 QSV 提交仍保持约 11/21 ms 双峰，则 CBR 并非主要原因，停止在码率控制上试探，转向既有 FFmpeg 同步等待源码与驱动边界。若显著缩短，再用同条件复测确认，且不把一次最低帧当下限。损坏码流或不同内容导致的无法比较如实标注。

固定质量第一次对照得到 CPU RGB 12.283 ms（回读约 3.200 ms，编码提交约 8.807 ms）、CPU YUV 12.600 ms、GPU RGB→QSV 11.195 ms；三条均通过严格解码。随后固定质量 GPU NV12→QSV 通过解码，但 18.401 ms（转换提交约 0.679 ms，编码提交约 17.430 ms），没有显示去掉驱动内部 RGB 转换的收益。不同运行的屏幕内容不完全一致，这些数字是观测值，不能直接宣布正式排序。

**下一次唯一 CPU 对照**：CPU RGB 保持原始屏幕、固定质量 CRF 23、同样 x264 ultrafast/zerolatency 与格式路径，仅把切片编码线程从 4 改为 8；CPU 颜色转换路径和 GPU 不参与。x264 的 zerolatency 使用同帧切片并行，2880×1800 下四线程 8.807 ms 的编码段足够大，增加至八线程有可能带来约 1 ms 以上收益。只做一次短测和严格解码；若无明显下降，则不继续以线程数作为主要改进方向。若下降明显，只在同一场景稳定性检查后才称改进有效。

8 线程实际测到 CPU RGB 10.105 ms，其中提交 7.337 ms、回读 2.552 ms；相对先前 4 线程提交 8.807 ms 有下降。系统向本进程提供 16 个逻辑处理器，编码段仍达 7.337 ms。因此追加**最后一次 16 线程上界对照**，其余保持不变；无论结果如何停止线程数逐级试探。跨次运行的回读和桌面画面不同，只报告各自结果与可解释的变化，不能将总延迟差全算成线程收益。

16 线程的观察值 11.548 ms，但采样窗口平均约 38.7 Mbps，而 8 线程约 0.28 Mbps；说明真实桌面内容变化远大于线程方案差异，不能据此判断 8 和 16 谁快。固定场景成为必须完成的测量控制。

`tests/CaptureStimulus` 是一次性 Avalonia 测试窗口：覆盖主屏、固定静态网格和 30 FPS 移动小块。窗口只产生画面，所有被测路径仍用 DXGI DDA 捕获真实主屏；不读取视频文件作为编码输入。每条路径在同一窗口持续运行时各取预热 10 帧、正式 60 帧。测试脚本须在 finally 关闭窗口，不留下前台窗口。窗口绘制本身占用的 CPU/GPU 资源属于固定测试环境；结果仅作为此局部运动场景的条件下限，不能泛化为滚动和全屏视频。全屏运动场景需单列而非混入该平均值。

第一批控制场景发现，桌面 `LastPresentTime` 相邻帧平均间隔约 46.6 ms，约 21.5 FPS；这不满足目标的 30 FPS，第一批控制结果不得用于 30 FPS 下限认定。窗口的 33.3 ms `DispatcherTimer` 和采样循环的 `Thread.Sleep` 在 Windows 默认粒度下可能晚唤醒。两进程在其短暂采样生命周期内分别请求 1 ms 定时器分辨率，退出即释放。先用一条路径核实真实 `LastPresentTime` 间隔达到约 33.3 ms；否则继续处理节拍问题，不跑性能矩阵。[Windows timeBeginPeriod 文档](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)。

请求 1 ms 定时器分辨率后，实际源帧间隔仍约 34.52 ms，短窗平均不足 30 FPS。下一版让测试窗口以 36 FPS 提供源画面，采样仍限制为目标的 30 FPS；30 FPS 表示**采样/编码速率**，不要求本机显示源恰好 30 FPS。采样器改为绝对时间节拍，避免每次晚醒后重新起算 33.3 ms 造成系统性变慢。报告显式保存每个 Acquire 时间与正式样本的实际捕获 FPS，先检查约 30 FPS，再跑 CPU/GPU 矩阵。测试窗口视频速率不是用户目标的远程发送帧率。

## 无码率约束时的 CPU 无损候选（单独报告）

当前目标没有输出码率上限。既有 H.264 的最优 CPU 代表路径两轮约 8.34/7.98 ms，GPU QSV 两轮约 10.59/10.63 ms。LZ4 是成熟的快速无损编码器；8 条独立 BGRA 行带并行压缩，可省去 CPU YUV 转换，并提供可能显著低于 H.264 的捕获＋编码时间。该路径属于不同带宽/压缩率类别，绝不和受限带宽 H.264 混合排名。

固定实现：复用相同 DXGI DDA 主屏及 staging 映射，保留 2880×1800、32-bit BGRA、30 FPS；8 条行带各自使用 LZ4 fast，完整压缩后合并成一个含尺寸/步长/行带长度的自描述数据包。计时包括捕获、GPU→CPU 回读、并行压缩及合包复制。采样后的每帧通过独立解压和 SHA-256 与原始映射像素逐字节核对；输出实际 Mbps、平均/P95 和分层耗时。只在前述固定窗口下测试，窗口自动关闭。若码率远高于常见链路，报告“无约束压缩下限候选”，不宣称远程桌面可用带宽内的下限。

局部运动的 LZ4 两轮为 3.884/3.732 ms，30 FPS 左右，70/70 帧精确还原，约 23.6 Mbps；这证明原始彩色无损 CPU 路径可明显快于当前 H.264 路径，同时也表明其带宽条件不同。为防止局部运动掩盖全画面成本，测试窗口另提供 `--full-motion`：四种相近但不同的正常 RGB 彩色块在整个 2880×1800 屏幕以固定节拍轮换，即使捕获跨过一个源帧也保持画面变化。保持捕获源和测试步骤一致。只测试 LZ4 CPU、x264 CPU 最优代表、QSV 原始纹理三条路径；每条仍报告实际 FPS、平均/P95、Mbps 和严格解码。若窗口绘制拖慢实际 30 FPS，本组不得用来认定目标数值，不通过筛样补救。

## 当前已实现基线的参数（不是目标限定）

- 主显示器的 DXGI 原始像素尺寸，正常彩色；不缩放、不裁剪、不量化、不降位宽。也可明确指定其他显示器。
- 统一 H.264、默认 30 FPS 上限、5 Mbps 编码目标/上限、单帧大小的 VBV、无 B 帧。实际字节数另行报告，不宣称每帧大小恒定或短时绝不超过目标。
- 主指标：成功的 `AcquireNextFrame(0)` 调用开始，到当前 PTS 的完整编码包返回并复制为可发送字节的时间。包含回读、转换、驱动同步、编码、码流复制；不含下一帧等待、UDP、解码和显示。
- 同时记录桌面 `LastPresentTime` 到包返回的时间、开始捕获时源画面已经存在多久、累积桌面帧数、没有新画面的次数。
- 每路径默认预热 10 帧、正式 60 帧，采样最多 15 秒。首帧单列；样本不足、锁屏、设备错误、队列延迟等如实报告，不用旧帧凑数。

## 已实现的候选路径矩阵（不是必须全部完成的交付清单）

| ID | 路径 | 应回答的问题 |
|---|---|---|
| `cpu-rgb` | 桌面 → CPU 映射 → 借用 BGR0 → x264rgb | 不在应用层转 YUV、也不逐行复制时，实际耗时如何？ |
| `cpu-yuv` | 桌面 → CPU 映射 → 四线程转 YUV420P → x264 | CPU 转换的明确对照；转换源借用同一映射内存 |
| `gpu-nv12-cpu` | 桌面 → GPU 转 NV12 → CPU 映射 → 借用 NV12 → x264 | GPU 先转换、减少读回数据是否值得？ |
| `cpu-nv12-qsv` | 桌面 → CPU 映射 → 转 NV12 → QSV 上传/编码 | 有 CPU 回读/上传的硬编码对照 |
| `gpu-nv12-qsv` | 桌面 → GPU 转 NV12 → QSV 直接硬件映射 → 编码 | 无原始像素 CPU 回读路径 |
| `gpu-nv12-qsv-half` | 原始桌面 → GPU 缩到半宽半高并转 NV12 → QSV 直接硬件映射 → 编码 | 降低输出像素数时，完整出包耗时能下降多少；属于另一个画质条件 |
| `gpu-rgb-qsv` | 原始 BGRA 捕获纹理 → QSV | 当前 FFmpeg/驱动是否真正接受原始 RGB 纹理；失败直接报告 |
| `gpu-nv12-nvenc` | 桌面 → GPU 转 NV12 → NVENC | NVIDIA NV12 硬件纹理路径 |
| `gpu-rgb-nvenc` | 原始 BGRA 捕获纹理 → NVENC | 省去应用层转换的 NVIDIA 路径；驱动内部工作仍计时 |

所有 GPU 路径使用捕获显示器所在 D3D11 设备，不悄悄跨 GPU 拷贝。无 NVIDIA 编码能力的设备仍会保留 NVENC 初始化失败记录。失败不等于该格式在所有硬件上都不支持。

CPU 映射优先使用 DXGI 的系统内存桌面映射（仅当系统明确报告支持）；否则执行 staging 回读。不把 staging 回读称为“捕获零拷贝”。BGRA 与 BGR0 的 B/G/R 字节位置相同，第四字节在 BGR0 中忽略；没有通过换标签将 YUV 当 RGB。

CPU 映射内存通过引用计数 AVFrame 借用；编码器完成并释放引用后才解除映射。GPU RGB 路径借用原始捕获纹理并保留 COM 引用。编码器内部是否复制/转换不由接口名称推断。

## 计时及验证

- 每条路径独立进程；原始 FFmpeg 日志保存到该路径的 `stderr.txt`。初始化失败、崩溃、超时与样本不足分开，不静默换后端。
- QSV GPU 初始化修复验证：当前 FFmpeg 构建复用父 loader 创建编码 session 失败。在独立 worker 初始化时暂时清空公开 `AVQSVDeviceContext.loader`，让 avcodec 创建 loader，随后立即恢复父 loader。同一 D3D11 设备、纹理映射、编码配置和计时定义保持不变。FFmpeg 没有暴露新 loader 的所有权，因此它随 worker 退出回收；一次打开、一次测试后退出是强制边界。这是测试兼容性绕过，**不是可合入长期运行生产程序的生命周期修复**，报告必须标识。
- GPU 默认不插入额外 fence；准备阶段仅报告 CPU 提交时间，编码调用到完整出包包含尚未完成的 GPU 工作，不能称为“纯硬件编码耗时”。`--gpu-fence` 是单独的诊断方案，会改变同步行为，不能与默认结果混在一起。
- 完成采样并销毁编码器后，保存 `encoded.h264` 并统一软件解码所有包，逐帧检查 PTS、帧数、原始宽高与像素长度。解码启用 `err_detect=explode` 并检查原始错误/容错日志；返回了帧不等于码流正确。验证失败标为 `validation-failed`，保留计时与码流，不能列为通过。验证不与编码采样同时运行。
- 半尺寸路径改查 1440×900 输出尺寸，并要求解码内容确实随受控动态画面变化；原图同尺寸质量参考尚未建立，因此不输出伪造的 PSNR。
- 只在最后正式帧编码完成后复制该帧原图，计算与解码图的 RGB 误差、PSNR，保存原图和解码 BMP，供人工看文字与颜色。RGB 4:4:4 和 YUV420 的压缩/画质不同，不能仅按毫秒排名。数值误差不是人工画质结论。
- 保存逐帧耗时、平均/P50/P95/最大值、实际码流字节、名义 FPS 下码率及采样窗口码率。分配量/GC 计数明确包含最终参考截图，不伪装为纯编码器分配量。
- 此程序顺序采集真实桌面；不同路径的画面可能不同，输出不自动得出“同内容性能排名”或“硬件极限”。严格性能排序需要相同输入的另一个明确实验，不能把离线素材结果冒充实时捕获结果。
- 当前矩阵验证捕获至完整编码包，**不包含**切片提前输出/边编码边发送。这项需单独接入 SDK 回调，并单独测首片、末片及网络重叠，不用普通 FFmpeg 出包接口冒充实现。

## 编译与执行

需要 Windows x64、.NET 10，以及项目已有的 FFmpeg 8 共享库。发布形态依赖框架，非 AOT、非自包含；不需要修改生产 FRD。

```powershell
dotnet build .\tests\CaptureEncodeBench\CaptureEncodeBench.csproj -c Release

$bench = '.\tests\CaptureEncodeBench\bin\Release\net10.0-windows10.0.26100.0\CaptureEncodeBench.exe'
& $bench --list

# 只有显式 --run 才开始真实捕获和编码。运行期间保持桌面有变化。
& $bench --run --ffmpeg .\third_party\ffmpeg\runtime --output .\results\capture-encode-matrix-01

# 明确选择部分路径，仍使用相同固定配置。
& $bench --run --ffmpeg .\third_party\ffmpeg\runtime --output .\results\capture-encode-rgb-yuv-01 --routes cpu-rgb,cpu-yuv --bitrate-mbps 5
```

结果目录必须不存在或为空，避免覆盖证据。入口无参数或 `--help` 只显示说明，`--list` 只打印矩阵。主进程退出码：0 为全部完成或库未包含某后端，2 为存在失败/超时/不足样本，1 为命令或主进程异常；是否测到某路径始终以报告的状态和样本数为准。

`manifest.json` 在执行前记录矩阵、参数、程序及 FFmpeg DLL 的 SHA-256；`results.json` 汇总机器可读结果，`summary.md` 展示简表，各路径目录保存完整报告、原始日志与最后一帧的图像。
