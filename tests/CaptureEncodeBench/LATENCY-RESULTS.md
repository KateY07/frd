# 本机原始分辨率捕获＋编码短测

条件：Intel Arc 140T、2880×1800 原始彩色桌面、捕获上限 30 FPS。所有数字为去掉 10 帧预热后的 60 帧平均，起点是捕获调用开始，终点是**完整编码包**形成；不包含 UDP、解码、渲染，也不包含源画面出现到捕获调用开始的等待。每条路径独立进程，真实 DDA 屏幕捕获，结果与逐帧数据见下方目录。

| 场景与路径 | 第一次平均 / P95 | 复测平均 / P95 | 复测 FPS | 复测码率 |
| --- | ---: | ---: | ---: | ---: |
| 局部变化，CPU BGRA → 8 条带 LZ4 无损 | 3.88 / 6.48 ms | 3.73 / 5.78 ms | 30.01 | 23.57 Mbps |
| 局部变化，CPU BGR0 → x264rgb 16 线程 | 8.34 / 见原报告 | 7.98 / 见原报告 | 29.99 | 约 0.70 Mbps |
| 局部变化，GPU 原始纹理 → QSV H.264 | 10.59 / 见原报告 | 10.64 / 见原报告 | 约 29.8 | 约 0.12 Mbps |
| 全画面四阶段变化，CPU BGRA → LZ4 无损 | 3.98 / 5.79 ms | **3.40 / 4.27 ms** | 30.01 | 19.70 Mbps |
| 全画面四阶段变化，CPU BGR0 → x264rgb 16 线程 | 8.83 / 10.26 ms | **8.59 / 10.02 ms** | 30.00 | 17.92 Mbps |
| 全画面四阶段变化，CPU BGR0 → x264rgb 16 线程，2 Mbps CBR 上限 | — | **9.48 / 11.58 ms** | 30.02 | 1.12 Mbps |
| 全画面四阶段变化，GPU 原始纹理 → QSV H.264 | 10.72 / 11.68 ms | **10.70 / 11.13 ms** | 29.99 | 1.66 Mbps |

全画面复测的 LZ4 捕获帧有 4 个不同 SHA-256；60 个计时帧的 59 个相邻帧对全部不同。70/70 帧均由独立解码器逐字节还原。两条 H.264 路径也各有 70/70 帧严格解码通过。全画面 LZ4 复测耗时中，staging 映射平均 2.22 ms、并行压缩 0.99 ms；CPU x264rgb 为映射 2.51 ms、编码调用 5.92 ms；GPU QSV 无应用层读回，完整出包调用 10.57 ms。

本机**已测路径中的最低平均值**是 CPU LZ4 的 3.40 ms；不设带宽上限时，这是当前原始彩色方案的工程下限候选。GPU 纹理直接交给 FFmpeg QSV 的已测值为 10.70 ms，其中驱动等待和编码器内部工作无法由当前接口拆开。CPU 无损、CPU H.264、GPU H.264 的码率和画质不同，不能把耗时差解释成同等码率、同等画质的编码器排名。GPU 路径还有一次性 worker 的 FFmpeg QSV loader 兼容绕过，并非生产生命周期修复。

2 Mbps CPU H.264 复测使用 `-b:v 2000k -maxrate 2000k -bufsize 66667`，因此是上限而非强制填满的发送速率；在这一固定、块状的全画面刺激下，实际采样窗口为 1.20 Mbps。70/70 帧可解码，但最后一帧 RGB PSNR 约 23.84 dB，说明它以可见画质损失换取了带宽约束。此路径仍为 RGB 4:4:4 的 `libx264rgb`，不是通常远程桌面会使用的 YUV420 H.264。

30 FPS 采样带来的源画面等待另计：全画面 LZ4 复测中，DDA 源时间戳到取得帧平均约 15.28 ms，源时间戳到完整压缩包估算约 18.57 ms。因此 3.40 ms **不是**画面变化到网络可发送的完整等待时间。上述数字也不是 Intel Arc、CPU 或所有画面内容的物理绝对下限。当前代码没有表明继续微调 x264/QSV 参数会有显著收益；要降低 LZ4 路径，主要成本是 GPU→CPU 映射。只有明确可验证的替代捕获/传输机制或硬件接口才值得再开一组实验。
